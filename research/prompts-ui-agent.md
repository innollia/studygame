# 조사 프롬프트 8 — UI 평가 서브에이전트 설계 (2026-10-24)

아래 블록 전체를 조사 에이전트에 붙여 넣는다. 결과는 `research/8-ui-evaluator-agent.md`로 받는다.

```
[배경]
나는 고등학생 두 명(아안, 파이)의 게임기획 독학 프로젝트를 관리하는 매니저(Claude Code 위에서 도는 오케스트레이터)다. 두 사람은 "AI로 게임을 만드는 팀"이다. 엔진 사용법이나 코드 구현은 공부하지 않고 기획, 분석, 플레이어 경험, UI/UX, AI 트렌드를 공부한다. 작업 공간은 디스코드와 피그잼(FigJam)이다. 둘은 이미 이런 활동을 해 봤다. 앱 UI를 유튜버가 피드백하는 영상을 보기 전에 각자 먼저 피드백하고, 그다음 유튜버 피드백과 비교한다. 이 방식이 효과가 좋았다.

이제 "게임이나 기획서를 주면 UI를 평가하는 서브에이전트"를 만들려고 한다. 쓰임새는 두 가지다.
(1) 제작 도구: 게임잼 빌드, 스크린샷, 플레이 영상, 웹 빌드 링크, 기획서(화면 설명·와이어프레임)를 주면 UI 문제를 찾아 우선순위를 매겨 준다.
(2) 학습 도구: 두 사람이 먼저 평가하고 나서 에이전트 평가와 비교한다. 또 두 사람의 UI 평가 자체를 채점·피드백해 준다.
실행 환경은 Claude Code다. 서브에이전트 정의(.claude/agents/*.md), 스킬, 이미지 입력, 브라우저 자동화(Playwright 등)를 쓸 수 있다. 모델은 Claude(Opus/Sonnet급)다.

[조사할 것]
1. 게임 UI/UX 평가 기준
   - 일반 휴리스틱(Nielsen 10)과 게임 전용 휴리스틱을 비교하라: Pinelle 외(2008) game usability heuristics, Desurvire의 HEP/PLAY, Federoff, Celia Hodent의 The Gamer's Brain(usability와 engage-ability의 기둥).
   - HUD 분류(diegetic / non-diegetic / spatial / meta, Fagerholt & Lorentzon), 정보 위계, 가독성·대비(WCAG 대비 기준을 게임에 적용할 때의 한계), 피드백·반응(입력 → 반응), 온보딩, 접근성(Game Accessibility Guidelines, Xbox Accessibility Guidelines).
   - 각 기준이 "스크린샷만으로 판단 가능 / 영상이 필요 / 직접 플레이해야 함" 중 무엇인지 분류하라.
2. LLM·비전 모델로 UI를 평가할 때의 근거
   - 멀티모달 LLM의 UI 휴리스틱 평가·디자인 비평 연구(예: UICrit 데이터셋, LLM 자동 UI 피드백 연구 등). 전문가 대비 정확도, 자주 틀리는 지점(없는 문제를 지어냄, 시간에 따라 변하는 피드백과 손맛은 판단 불가, 위치를 잘못 지목함), 심각도 판단의 신뢰도를 정리하라.
   - 정확도를 높이는 방법: 근거(화면 좌표·영역·타임스탬프)를 강제하기, 체크리스트 방식과 자유 비평의 차이, 여러 관점 패스 후 합치기, 자기 검증 패스, 확신도 표시.
   - 입력별 차이: 스크린샷 묶음, 영상 프레임 추출, 웹 빌드를 브라우저로 직접 조작하며 캡처, 기획서만 있을 때(설계 비평).
3. 서브에이전트 구성안 비교
   - A안: 체크리스트를 가진 단일 에이전트.
   - B안: 관점별 전문 에이전트(가독성·위계, 피드백·반응, 온보딩, 접근성, 모바일·입력 등)와 그 결과를 합치는 에이전트.
   - C안: 그 밖에 근거 있는 구성.
   - 정확도, 비용, 시간, 유지보수 측면에서 비교하고 하나를 추천하라.
   - 출력 형식(스키마)을 제안하라: 문제 / 위치(좌표·화면·시점) / 근거 / 어긴 기준 / 심각도(Nielsen 0~4 등) / 확신도 / 수정 제안 / "사람 플레이테스트로 확인 필요" 표시.
4. 학습용 모드
   - 학습자가 먼저 평가하고 나중에 비교하는 "블라인드 비교" 모드 설계: 에이전트 답을 언제 공개할지, 학습자 평가와 에이전트 평가를 어떻게 맞대어 보여줄지, 둘이 다를 때 누가 맞는지 판단하는 법.
   - 학습자의 UI 평가를 채점하는 루브릭 4~5기준(관찰의 구체성, 기준 연결, 심각도 판단, 수정 제안의 실현성 등).
   - 학생이 AI 평가를 정답으로 외워 버리는 위험과 대책.
5. Claude Code에서의 구현 방법
   - 서브에이전트 정의 파일의 구성(이름, 설명, 허용 도구, 모델), 스킬로 만들 때와 서브에이전트로 만들 때의 차이, 이미지·영상 전달 방법, 웹 게임을 브라우저로 열어 캡처하는 흐름, 한 번 평가에 드는 대략의 비용·시간. 공식 문서를 우선 출처로 쓰라.
6. 검증 계획
   - 이 에이전트가 쓸 만한지 확인하는 방법: 전문가 비평(예: 유튜버의 UI 피드백 영상)과 일치하는 비율, 두 학습자 평가와의 비교, 지어낸 문제의 비율. 첫 2주 시험 절차를 제안하라.

[산출물]
- 맨 위에 핵심 결론 5줄.
- 추천 구성안 하나와 그 이유.
- 서브에이전트 시스템 프롬프트 초안: 한국어. 입력 종류별 처리, 체크리스트, 출력 스키마, 지어내기 방지 규칙 포함.
- 체크리스트 표: 기준 / 무엇을 보나 / 판단에 필요한 입력(스크린샷·영상·플레이) / 출처.
- 학습용 블라인드 비교 절차와 학습자 평가 루브릭.
- 검증 계획.
- 모든 주장에 출처 URL. 논문·공식 문서를 우선한다. 근거가 약하면 "근거 약함", 확인 못 했으면 "미확인"이라고 쓴다.

[답변 규칙]
한국어로, 고등학생도 읽을 수 있는 쉬운 말로 쓴다. 일반론으로 끝내지 말고 바로 만들 수 있는 수준까지 구체적으로 쓴다. 엔진 사용법이나 코드 구현을 공부시키는 내용은 넣지 않는다(이 팀은 AI로 만든다).
```
