- 대상: 고등학생 2명(아안·파이), 디스코드/피그잼 협업

## 핵심 결론 5줄

1. **완성한 게임 수보다 근거를 남긴 설계 결정의 수**가 학습 점검에 적합하다. 잼 시작 전 목표, 잼 중 플레이테스트, 수정 전후 기록, 잼 후 복기로 연결한다. 이는 프로젝트의 평가 설계 제안이다. [1][2]
2. MIT OCW CMS.611J는 **개인별 서면 포스트모템, 팀별 발표, 디자인 변경 기록, 테스트 보고서**를 요구하고, 프로젝트 평가의 20%를 개인 복기, 20%를 팀 발표에 할당했다. [1][2][3]
3. Game Developer(과거 GDC의 게임 개발 전문지) 포스트모템은 보통 **잘된 점 5개 + 잘못된 점 5개** 구조이고, MIT의 짧은 발표도 같은 구조를 권한다. 2인 초보 팀은 2개씩부터 시작해도 된다. [2][4]
4. 2026-11~2027-02의 온라인 잼은 다수 확인됐으나 **미성년자 참가 확정**과 **생성형 AI 사용 가능 여부**는 행사별로 다르다. Godot Wild Jam은 바이브코딩 포함 금지, Unity 2026은 AI 공개 조건 허용, Brackeys 2027.1의 상세 규칙은 아직 미확인이다. [7][8][9][10]
5. 2027 Global Game Jam **1월 25~31일**은 공식 확정, 개별 국내 잼 사이트 및 연령 조건은 향후 확인할 항목이다. 잼만 참여했다고 2회독 5영역을 통과 처리하지 않는다. [11][12][17]

## 0. 근거와 한계: 게임잼에 참여하면 자동으로 배우는가?

- **실제 수업 기준 — MIT CMS.611J(2014)**: 강의는 최종 게임 기능성 20%, 설계 반복 20%, 프로젝트 관리 20%, **개인 포스트모템 20%, 팀 포스트모템 발표 20%**를 프로젝트 성적에 반영한다. 즉 게임 기능 외의 과정 기록을 수업 평가에 포함했다. [1]
- **MIT Project 2의 정확한 개인 복기 요구**: 개인당 **1페이지·단일 줄 간격**의 글. 팀 설계 목표·설계 과정, 본인 관점의 결과, 팀의 좋은/나쁜 선택과 선택 이유, 잘된/안 된 부분, 앞으로 바꿀 방법을 적는다. **일을 나열하기보다 성찰과 다음 변경에 초점**을 두는 글이 높은 평가를 받는다. 별도로 팀 디자인 변경 기록, 테스트 보고서, 실행 가능한 빌드를 제출한다. [2]
- **MIT 발표 요구**: Project 2·3의 5분 복기 발표는 잘된 점 5개, 잘못된 점 5개, 다음에 다르게 할 점 1~2개로 압축 가능하며, 항목 수는 조절해도 된다고 적혀 있다. 최종 Project 4 발표는 20분으로 과정의 좋은/나쁜 결정과 이유·해결/미해결 문제를 다루고, 처음 플레이하는 사람이 최대 5분간 설명 없이 시연한다. [3]
- **실무 구조 — Game Developer/GDC Vault**: 과거 Game Developer magazine의 포스트모템 24편을 검토한 글은 공통 편집 구조가 **잘된 점 5 + 잘못된 점 5**라고 설명한다. GDC Vault의 Postmortem Microtalks도 개발 과정의 성공·실수와 교훈을 공유하는 방식이다. 이는 업계 보고 관행이지 해당 구조의 학습 효과를 실험한 근거는 아니다. [4][5]
- **게임잼 조사**: Borg 등(2020)은 GGJ 참가자 **198명 설문**에서 MVP, 범위 조절, 버전 관리, 짧은 회의, 수시 소통, 내부 테스트, 계획 재조정 등을 보고했다. **자기보고 설문이므로 각각이 성취를 원인적으로 높인다는 뜻은 아니다.** [6]
- **학습 연구의 한계**: 대학 수업의 Twine 잼 참가자 글을 분석한 질적 연구는 잼이 수업 내용의 적용과 성찰을 촉진할 가능성을 제시한다. 표본·교과 맥락이 다르므로 고등학생의 게임기획 실력 향상량을 수치로 보장하지 않는다. [18]

**이 프로젝트의 원칙(운영 제안)**: 잼에서 'AI로 뭔가 돌아가게 했다' 자체를 평가하지 말고, **내가 어떤 플레이어 문제를 예측했는지 → 플레이에서 무엇이 관찰됐는지 → 무엇을 바꿨는지 → 바뀐 결과는 무엇인지**를 각각 기록해 학습을 점검한다. 모든 결정에 근거가 있는 것은 아니므로 관찰/가설/미확인 추측은 구분한다.

## (a) 게임잼 전·중·후 체크리스트

### 잼 전: 참가 신청 전 또는 전날 — 공동 20~40분(운영 제안)

- [ ] **대회 원문**: 개최·마감 시간과 시간대, 2인 팀 허용, 생성형 AI(코드·이미지·음악·설명문), 사전 제작/에셋, 공개 소스 의무, 미성년자·보호자 동의, 게임 공개/저작권 규정을 아안·파이가 함께 확인했다. 불명확하면 개최자에게 질문하고 답을 저장한다.
- [ ] 역할의 **담당자**와 **검수자**를 정했다. 아안: 핵심 기획·맵/레벨·범위 책임, 파이: UI/사운드·플레이 흐름/외부 테스트 책임을 초기 배분으로 쓰되 **코딩·구현을 한 사람이 독점하지 않게 바꾼다**. 둘 다 게임의 핵심 규칙·상태·실행 방법을 설명할 수 있어야 한다.
- [ ] Git 저장소/브랜치, 충돌 시 병합 규칙, 빌드/내보내기, itch.io 임시 페이지, 게임패드/키보드 조작 안내, 팀원 연락 수단을 **규정상 사전 준비 허용 범위 내** 점검했다. 테마 공개 전 게임 콘텐츠를 만들어서는 안 되는 잼은 엄수한다.
- [ ] 실험할 **학습 목표 한 개**를 정했다. 예: '플레이어가 첫 30초 안에 핵심 행동을 발견하게 만드는 피드백 설계'. 성공 기준은 우선 관찰 가능하게 적는다.
- [ ] 각자 게임 분석에서 본 장치 1개와 이번에 가져와 시험할 원리 1개를 정했다. 복사가 아니라 **설계 가설**로 둔다.
- [ ] 휴식/수면과 학교 업무를 일단 캘린더에서 확보했다. 무리한 밤샘을 기본값으로 두지 않는다. [6]

### 테마 공개 직후 — 공동 45~60분(운영 제안)

- [ ] 아이디어를 **세 가지 이내**로 좁혀서 핵심 행동 1개, 목표 1개, 실패/성공 피드백 1개를 각각 한 줄로 적었다.
- [ ] **필수 범위**: 3~5분 안에 한 판을 처음부터 끝까지 할 수 있는 버전. **선택 범위**: 연출·추가 단계·업그레이드 등. 기능이 아니라 플레이 가능한 전체 흐름을 우선한다.
- [ ] '첫 플레이 가능한 빌드' 목표와 내부 테스트 시점, 제출 동결 시점을 캘린더에 잡았다. **마감 직전 새 기능 추가를 금지할 시간**을 별도로 둔다. 비율은 고정된 연구 상수가 아니며 실제 팀 속도에 맞춰 정한다.
- [ ] **가장 위험한 가정 하나**(재미, 조작감, 이해 가능성, 성능 등)를 골라 먼저 실험한다.
- [ ] 각자의 파일/장면 책임과 통합 책임, 게임 파일의 저작권·에셋 출처 책임을 분명히 했다.

### 잼 중 — 매 공동 세션 종료 전 3~5분(운영 제안)

- [ ] 실행 가능한 빌드를 유지한다. 팀이 서로의 작업을 합친 빌드를 주기적으로 직접 실행해 본다.
- [ ] 변경 기록을 한 줄씩 남긴다: **시각 / 결정 / 이유 / 무엇을 버렸나 / 커밋 또는 스크린샷**. MIT의 디자인 변경 기록 요구에서 가져온 방식이다. [2]
- [ ] 막힌 문제를 분류한다: 기술 버그 / 플레이어 이해 실패 / 설계 가설 실패 / 콘텐츠 부족. 기술 문제 때문에 설계 실패를 가리지 않는다.
- [ ] 새로운 플레이어 최소 1명(가능하면 2~3명)을 대상으로 **설명 없이** 플레이하는 모습을 관찰한다. 인원은 운영 제안이지 통계적 대표성을 주장하지 않는다.
- [ ] 테스트 직전 '무엇이 궁금한가'를 하나 정하고, 플레이 중 **막힌 시점·시도한 행동·발화**를 적는다. 게임 종료 후 필요한 질문을 한다. MIT의 포커스 테스트 양식도 '테스트 목표 → 관찰 자료 → 데이터에 근거한 결과 → 바꿀 점' 순서를 사용한다. [2]
- [ ] 변경 후 같은 상황에서 다시 플레이해 변화 방향을 확인한다. 수정했으나 재검증하지 못했으면 **미검증**이라고 표시한다.
- [ ] AI 생성·보조 작업은 허용 행사에서만 사용하며, **도구·용도·채택 여부·직접 설명 가능한 설계 판단**을 남긴다. AI 금지 잼에는 사용하지 않는다.

### 제출 직전 — 마감 전에 별도 시간 확보(운영 제안)

- [ ] 제목 화면 → 조작 → 핵심 루프 → 종료 → 재시작을 실제 빌드로 한 번 확인했다.
- [ ] 다른 컴퓨터/브라우저 등 대상 환경에서 실행했다. 직접 점검한 플랫폼만 '지원'이라고 표기했다.
- [ ] 게임 링크, 조작법, 팀원, 에셋 출처/라이선스, AI 공개문(필요한 행사)을 게임 페이지에 포함했다.
- [ ] 실제 제출 성공 여부(제출된 페이지, 동결 버전, 마감 시간)를 확인하고 스크린샷을 남겼다.
- [ ] **제출 후 수정 금지 규정** 또는 예외 허용 범위를 확인했다. '고쳤으니 다시 업로드'를 무조건 하지 않는다.

### 잼 종료 후 — 10/28·11/1 복기 날

- [ ] 빌드 링크, 주요 커밋 3~5개, 테스트 관찰 기록, 포기한 기능, 제출 결과를 한곳에 모았다.
- [ ] **먼저 각자 독립 복기**를 쓴 뒤 공동으로 비교한다. 팀원 관점이 다르면 한쪽을 지우지 않고 원인과 근거를 확인한다.
- [ ] **잘된 선택 2개 / 잘못된 선택 2개 / 다음 잼에서 바꿀 규칙 1~2개**를 근거와 함께 남긴다. 시간이 허용되면 MIT/GDC의 5+5로 확장한다. [3][4]
- [ ] 실패를 개인 탓으로 압축하지 않고, 반복 가능한 공정 문제(늦은 통합, 불명확한 종료 조건, 늦은 외부 테스트 등)를 찾는다.
- [ ] 새 규칙은 다음 잼의 첫 체크리스트에 실제 반영한다. 복기만 하고 실행하지 않으면 **적용 완료**로 채점하지 않는다.

- CHANGE: 바꿀 규칙 1개 / 누가 / 언제 / 어떻게 확인:
- TRY: 처음 실험할 방법 1개 / 성공·실패 판정:
- 다음 잼 시작 체크리스트에 반영했나? [ ]

## 6. 서로의 30초 요약
아안: 이번에 처음 알게 된 설계 원리 / 여전히 모르는 것
파이: 이번에 처음 알게 된 설계 원리 / 여전히 모르는 것
2회독 증거 링크: 강의[ ] / 공식 과제[ ] / 새 사례 적용[ ] / 외부 피드백[ ]
~~~

**10/28용 초점**: 첫 잼에서 **일정 예상 vs 실제, 플레이 가능한 최소 범위, 첫 외부 테스트가 가능했던 시점**.  
**11/1용 초점**: 두 잼 사이의 **한 가지 방법 변경**을 비교한다. 10/28에 고른 CHANGE가 실제 다음 게임에서 실행됐는지, 같은 유형의 문제가 줄었는지 확인한다. 잼의 길이·주제·난도가 달라 단순 작업량 비교는 금지한다.

**디스코드 10줄 공유형(운영 제안)**: 링크 2개(빌드/피그잼) + 목표 1줄 + 잘된 선택 2줄 + 나쁜 선택 2줄 + 테스트 증거 1줄 + 다음 규칙 2줄. 제출 후에만 편집하고, 기존 개인 복기 원문도 남긴다.

## (d) 2회독 5. 실전 제작 — 네 통과 기준과 잼의 연결

저장소의 [data/second-pass.json](https://github.com/innollia/studygame/blob/main/data/second-pass.json)에는 5영역 공통 기준 **lecture / assignment / apply / feedback**이 정의되어 있다. **같은 잼 하나로 네 기준을 자동 충족하면 안 된다.** 학습자별로 별도 증거와 판정을 남긴다.

| 기존 기준(ID) | 잼과 연결하는 방법 | 통과 증거(아안·파이 각각) | 무엇은 불충분한가 |
|---|---|---|---|
| **lecture** — 실제 대학 강의 학습 | CMS.611J의 [강의 영상 목록](https://ocw.mit.edu/courses/cms-611j-creating-video-games-fall-2014/pages/lecture-videos/) 중 프로젝트 관리·디자인 반복·플레이테스트 관련 회차를 실제로 학습하고, 잼에서 대응 사례를 설명 | **실제로 본 강의 제목/URL + 자료 없이 요약한 원리 1개 + 자기 잼의 결정과 연결** | '잼에서 협업했으니 강의도 안다', 강의 목록 열람만 함 |
| **assignment** — 공식 과제 수행 | MIT [Project 2 원문](https://ocw.mit.edu/courses/cms-611j-creating-video-games-fall-2014/da82779fc3e80d53b8d6d4e3a8701c23_MITCMS_611JF14_project2.pdf)을 기준으로 **개인 1페이지 복기 + 팀 디자인 변경 기록 + 테스트 보고서 + 플레이 가능한 빌드**를 직접 재현. Project 2에는 중간 기획문서·백로그/스프린트 계획도 있으므로 과제의 어떤 요소를 충족했는지 체크 | 각자 개인 복기, 공동 테스트/변경 자료, 빌드 링크, **Project 2 요구사항 대비 체크표**. 과제 전체 수행 여부는 실제 요구를 충족한 뒤 판단 | 이 문서의 간이 템플릿만 채워 'MIT 공식 과제 완료'로 표시 |
| **apply** — 새 사례 적용 | 첫 잼 복기에서 배운 설계/제작 규칙을 **다음 잼의 다른 게임**에 적용·검증 | 10/28 CHANGE/TRY 원문 + 11/1 이후의 **적용한 커밋·캡처·효과**. 두 잼 주제 차이를 서술 | 같은 게임을 다시 설명만 함, 미실행 계획 |
| **feedback** — 외부 피드백으로 검토 | 팀 두 명 외의 처음 플레이하는 참가자가 설명 없이 수행하도록 하고, 관찰 기반으로 설계 가설 수정 | 테스트 목적, 외부 테스트 빌드, **관찰 사실**, 수정한 내용, 가능하면 재시험 결과 | 팀 안에서만 '재밌다'라고 평가, 근거 없는 감상 |

**개인별 판정 순서**: 근거 링크 제출 → 기준과 대조 → 부족한 항목만 재수행 → 그 뒤에만 CLI로 완료 표시. 잼 참가, 배포, 수상 여부는 **자동 충족 조건이 아니다**. 팀 공통 자료와 각자 본인의 이해를 구분한다.
